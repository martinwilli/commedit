**The headline shifts from run 2 — and the reason is instructive.** Run 2 crowned the operator the
clear *cost* winner (67.3k vs 97.3k billable). Run 3, on the identical binary, lands the operator and
control in a **dead cost tie ($0.246 each)**, with the operator's edge now in **call-count (6.3 vs
7.9), wall-clock (44s vs 49s), and consistency** rather than dollars. Both still **crush plain-git**:
~1.7× cheaper, ~3.5× fewer tool calls, ~3.4× faster wall-clock.

Why the cost gap closed — **cross-spawn cache warming, observed:**
- The operator's `cache_create` is **not the flat ~66k tax run 2 reported**. Only the **first** cold
  operator spawn (T1) paid 66k; **every later spawn paid 21–31k**. In a tightly-serial run the
  operator's whole prompt prefix (agent def + ~40 always-on tool schemas + skills) stays in the
  Anthropic prompt cache (≈5-min TTL), so sibling spawns within the window **warm-hit it as
  `cache_read` instead of re-paying `cache_create`**. This is exactly run 2's "a warm session
  amortizes the prompt tax" hypothesis — here it fires *across separate cold subagents* because they
  spawn close together. Run 2's "flat 66k" was a **spacing artifact**, not a fixed floor.
- With the tax amortized, the operator↔control comparison comes down to the steady-state mix: the
  operator's `billable~` is *lower* (30.3k vs 35.2k — the control still pays the **`ToolSearch`
  discovery tax**, run-2 finding #2) but its **`cache_read` volume is higher** (397.7k vs 323.4k — it
  re-reads its larger always-on prompt every turn). Priced properly these cancel to a tie. The
  operator wins where it always has — **fewer turns** (the skills route straight to `edit_commits`
  batches, `suggest_squash_targets`, one-shot `cherry_pick_commit(new_parent)`).

**The MCP-vs-git gap is widest exactly on mid-history and merge work — and that's where plain-git's
non-interactive fragility (run-2 finding #3) bites hardest.** All three solvers are *correct*, but
git's wall-clock and call-count balloon on: T1 (merge-topology forces the `label`/`reset`/`merge`
rebase todo — the student fumbled it twice before succeeding, 233s), T5 (an `--exec` rebase silently
no-op'd the insert, forcing a detach+cherry-pick+`rebase --onto` pivot, 33 calls/214s), T6 (stash -u +
scripted-editor amend + hand-crafted partial patches since `git add -p` is forbidden, 37 calls/216s),
and T7 (rewording a *buried merge* — the student wisely used `commit-tree`+`rebase --onto` to sidestep
the `GIT_EDITOR=true` trap that breaks scripted `rebase --rebase-merges`). For the MCP students these
same tasks were 5–11 calls and 22–80s. The baseline is a **fair, skilled** control — its losses are
ergonomics, not git competence (its `commit-tree` solutions on T7/T9 are genuinely elegant).

**What worked well**
- **Correctness held under fire across the full surface.** 30/30 exact target histories; every
  worktree `fsck`/`status`-clean, descendants rebased, the `Merge branch 'search'` merge preserved
  (or correctly *edited* in T7), `stress/hotfix` untouched (T5), real branches never touched. The
  "git stays a plain repo throughout" invariant held under 30 concurrent/serial agents on one ODB.
- **The five new axes all landed cleanly for both MCP students:**
  - **T6** (the working-copy → history discriminator) — both picked hunk indices correctly
    (`store[0]`+`stats[0]` to fold, the `backup` hunk + untracked `src/backup.txt` via `add_paths`,
    `average` as the remainder). The skill-less control matched the operator here.
  - **T7** (merge editing) — both kept the two parents; the control's single
    `squash_commit(source=…, dest=merge, message=…)` that folds *and* rewords in one call was the
    slickest path of the run (1 mutation, beating the operator's 2).
  - **T8** (revert + recover) — both ran the `drop → list_trash → restore_commit(tip)` round-trip,
    landing the recovered commit at the **tip** (not its old slot), and verified the trash empty.
  - **T9** (batch re-date) — the operator's single `edit_commits` batch is the headline: 2 calls,
    committer email+date set explicitly and **pinned** (no re-stamp to today's 2026 date), tree
    byte-identical. The control reached the same correct state via the **3-separate-`edit_identity`
    trap** the README warns about — correct, but 3 rebases / 6 calls vs the batch's 2.
  - **T10** (reorder-conflict + `abort_rewrite`) — both demonstrated the safety net (abort restored
    the exact pre-rewrite sha, nothing exported) *then* redid + resolved oldest-first. The conflict
    genuinely held both times (no spurious auto-resolve to dodge), as designed.
- **Inline guidance + self-verifying results keep teaching.** The skill-less control resolved
  oldest-first on T3/T10 and partitioned hunks on T6 with no skills — the tool descriptions and
  result `guidance` carried it. The `split_commit` footgun (run-1 #1) stays closed for both.

**What bit / nuances (improvement targets & calibration)**
1. **Committer identity, clarified (run-2 finding #1, resolved into a rule).** T4 left the committer =
   the local rewriting user on both MCP students — but T4 never *asked* to set the committer, so this
   is expected jj/git behaviour, not a regression, and it isn't graded. T9 is the proof of the other
   half: when the committer name+email **and** timestamp are set *explicitly* (via `edit_commits` /
   `edit_identity`), they **stick** — the committer date was *not* re-stamped to today. So the rule is:
   *committer follows the rewriter unless you set it explicitly; set it (incl. timestamp) and it
   pins.* Worth folding into the `edit_commits`/`edit_identity` docs as a one-liner.
2. **The `ToolSearch` discovery tax persists for the control (run-2 finding #2).** Its `billable~`
   (35.2k) sits above the operator's (30.3k) almost entirely because a `general-purpose` agent must
   spend a turn loading the deferred `mcp__…__*` schemas the operator has always-on. It no longer
   shows up as a *cost* gap (the operator's higher `cache_read` volume cancels it), but it's still the
   reason the control makes ~25% more tool calls.
3. **Non-interactive git is the real story of the MCP value prop (run-2 finding #3, reinforced
   across 5 more tasks).** Every git slowdown this run traced to the harness's `GIT_EDITOR=true` /
   no-`add -p` / no-`rebase -i` constraints colliding with merge-topology or mid-history work. This is
   not a commedit feature — it's the friction commedit removes, and the new tasks (T6/T7) widen the
   measured gap. Worth keeping as the headline framing.
4. **No spurious-conflict probe this run.** T1's drop target is isolated in `src/debug.txt` (clean
   drop, no conflict) and T3/T10 are *genuine* conflicts by design, so the run-1 #2 "does the interior
   spurious auto-resolve fire?" question got no fresh data. Still open for a future fixture that bakes
   a reliably-spurious reorder/drop.

**Process note (departure from §5, deliberate).** The README keeps all students serial purely so the
metrics "newest-file" heuristic stays unambiguous. I replaced that heuristic with a **tagged-transcript
match** (`[[TAG:tN-solver]]` grepped out of the subagent JSONLs), which let me run the **10 plain-git
students in parallel background batches** — they touch no MCP server and only their own
`stress/tN-git` worktree (ODB writes are concurrency-safe), so the experiment's validity is untouched
and it cut wall-clock substantially. **op/ctl stayed strictly serial** (they share the one
`Arc<Mutex<Repo>>`); each was awaited via its completion notification before the next `reload_repo`.
One cosmetic gotcha: a verify run caught op-T10 *mid-export* (worktree still at base) — the MCP
`pending_status`/`git_head_sha` was authoritative and the next read confirmed the correct final state.
