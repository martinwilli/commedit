# Run 4 — 2026-06-20 (THE GREAT PARALLELISM: all 40 students at once)

First run on the **multi-tenant** MCP server (`commedit-mcp` md5 `6e2455f6`) — the build that hosts
one editing session per branch (`feature/multi-tenant-sessions`: commits `ef03562`, `d03ce6f`,
`bc5a585`, `97083384`). Run 3 kept the two MCP students (operator, control) strictly serial because
they shared one `Arc<Mutex<Repo>>`; this build gives each branch its **own** session, so for the
first time **all 40 students ran concurrently**: 10 tasks × {operator, control, plain-git/Sonnet,
plain-git/Opus}, over **20 independent worktree-bound sessions** in one server plus 20 plain-git
worktrees. Every student was launched as a background agent in two back-to-back fan-outs (T1–T5,
then T6–T10) and left to run.

**Engine rewrite logic is byte-identical to runs 2/3** (`git diff 4fb7e54..HEAD -- crates/commedit-engine/src`
is empty — only the MCP session layer and the dogfood fixture's `gito` worktrees changed), so run-3's
answer keys hold; calibration this run was just re-deriving change ids. The students themselves are
the live confirmation.

**Result: 40/40 work-correct.** Every student produced the exact target history (verified out-of-band
from `git`: 264/264 ground-truth assertions pass). **But the parallelism exposed a real concurrency
bug:** a ref-write race on the shared `.git` silently **reverted 3 students' correct results** after
they finished (and 3 more hit it and self-recovered mid-run). See the headline finding below. All six
were recoverable from reflog.

## Headline 1 — the parallelism works: 9.9× wall-clock, no deadlock

All 40 students finished in a **407s wall-clock window** (19:44:04 → 19:50:51). The sum of per-student
spans — what a strictly-serial run would cost — is **4032s (~67 min)**, so the parallel run was
**9.9× faster end-to-end**. The one server held **22 concurrent sessions** (launch + cal + 20
stress) and stayed responsive throughout; `list_sessions` after the storm returns all 22 healthy. The
three-tiered locking held: **no deadlock**, distinct sessions ran genuinely in parallel, and the work
landed correctly in every one of the 40. The headline run-3 ergonomics all reproduced (operator
routes straight to `suggest_squash_targets` / `edit_commits` batches / one-shot
`cherry_pick_commit(new_parent)`; the skill-less control kept up via tool descriptions + result
`guidance`; the `split_commit` footgun stayed closed for both MCP students on T2).

## Headline 2 — the great parallelism exposed a ref-write race on the shared `.git`

This is the run's real finding, and it only appears under heavy concurrency. **Six of the 40 students
had a correct result silently clobbered by an empty-message ref write that reset their branch to an
earlier value** — the classic loss of a loose-ref update to a concurrent `pack-refs`/auto-gc on the
**one shared common-dir** that all 40 git-mutating processes (the plain-git students *and* the MCP
sessions' git-export bookkeeping) hammer at once.

- **3 students self-detected and recovered mid-run:** `t7-gito`, `t8-git`, `t8-gito` each reported
  "the branch ref reset back under me" and rescued the intact commit from the reflog
  (`t8-git` via `git merge --ff-only`). These verify clean.
- **3 students did not notice** (the revert landed *after* they verified and finished), leaving a
  failed git state at grading time:
  - `t9-git` — its 3-commit re-date rebase finished at `51becdb6` (correct), then the ref was reset to
    `stress/base` (reflog `@{0}` is an empty-message entry at base, sitting above the `rebase (finish)`).
  - `t6-git` — its tip `Add average stat` (`f457784c`) was reverted to its parent `Add backup command`,
    spilling the `average` change back into the working tree as an uncommitted `src/stats.txt`.
  - `t3-op` — its resolved drop exported to `3fe3440d` (correct), then the **git ref** was reset to
    base. Tellingly, the **MCP session still reports `head_sha 3fe3440d`** — the engine/jj state was
    correct the whole time; only the *exported git ref* was lost. (`t4-op` hit the same export-lag
    earlier but happened to `reload_repo`+redo and survived.)
- **All six are correct work, fully recoverable.** I confirmed each casualty's reflog sha holds a
  tree that meets the PASS criteria, then recovered `t3-op`/`t6-git`/`t9-git` from reflog — after
  which all 40 pass 264/264 ground-truth checks.

**Why it bites here and not in run 3:** run 3 ran the MCP students serially and only 10 plain-git
students in parallel; the ref write volume on the common-dir was far lower. Run 4 puts 40 ref-writers
(20 plain-git rebases/commits + 20 MCP exports) on one `.git` simultaneously, so concurrent
`pack-refs`/`gc --auto` and loose-ref writes race. The engine's stated invariant — *"distinct
branches export to distinct refs, so it's safe"* — holds for the **object** store (append-only,
hash-addressed, never corrupted) but **not** for **ref updates** under this much concurrency.

**Mitigations for the harness (the fix is in how we run, not the engine logic):**
1. Give each parallel student its **own clone / separate git common-dir** instead of sharing one (the
   strongest fix; removes all cross-process ref contention).
2. Or disable auto maintenance for the run: `git config gc.auto 0` (and `maintenance.auto false`) on
   the repo before launching, so no background `pack-refs` fires mid-run.
3. Or stagger/cap concurrency so far fewer ref writers overlap (run 3's de-facto safety).
4. The teacher must **verify out-of-band from `git` after the dust settles** (not trust student
   self-reports), since the revert can land post-completion — this run is the proof.

## Headline 3 — parallel cold-spawns cost more than run 3's serial spawns

Per-student `cost` rose vs run 3 (operator $0.246 → **$0.342**, control $0.246 → **$0.476**; git
~flat $0.416 → $0.437). The cause is the **inverse of run 3's happy accident**: run 3 found that
tightly-serial sibling spawns *warm-share* the operator's prompt prefix in the Anthropic cache
(~5-min TTL), so later spawns paid cheap `cache_read` instead of `cache_create`. Firing **40 cold
spawns at once** over a longer window defeats that warming — each pays more of the prompt-materialization
tax, and `cache_read` volume climbs because more turns happen (op calls 6.3 → 8.8, partly from
race-recovery and the export-lag reload). So the parallelism **trades cache efficiency for wall-clock**:
9.9× faster, ~1.4× pricier per operator student. The ordering still favors the MCP surface — operator
($0.34) is the cheapest solver, and both MCP students beat plain-git on calls (8.8/13.1 vs 22.8) and
wall-clock; control edged *above* git in dollars this run only because its `cache_read` ballooned with
the `ToolSearch` discovery turns under load.

**One Opus-specific quirk:** every `gito` student shows ~12.8k **uncached `input`** tokens per spawn
(vs ~40 for the Sonnet students, whose equivalent prompt is served as `cache_read`). The Opus
general-purpose subagent's prompt prefix wasn't cache-hit on cold spawn — a consistent, model-specific
billing difference, not extra work. It's a large part of why `gito` costs ~2.6× `git` ($1.14 vs $0.44)
on top of Opus's higher per-token rates.

## What reproduced from run 3 (the git-friction story, widened under load)
Every plain-git slowdown again traced to the harness's non-interactive constraints colliding with
mid-history/merge work, and parallelism added new variants:
- **T2 gito (322s, the run's longest):** discovered that git 2.53 silently ignores
  `GIT_SEQUENCE_EDITOR` when invoked as `rebase --onto X X` (onto == upstream short-circuits the
  editor); had to fall back to plain `rebase -i --rebase-merges <parent>` + `--no-autosquash` (to stop
  the floating `fixup! Add parser` from being folded). A genuinely subtle non-interactive footgun.
- **T7 (buried merge):** both git students used `commit-tree`(2 parents + body) + `rebase --onto` to
  sidestep the `GIT_EDITOR=true` trap that breaks scripted `rebase --rebase-merges` — elegant, but 18–21
  calls vs the MCP students' 6 / 15.
- **T6 (partial hunks):** no `git add -p`, so both git students hand-crafted `git apply --cached`
  patches; 34–38 calls vs the MCP students' 8 / 15.
- **T1 (merge topology):** `rebase -i` over the `Merge branch 'search'` merge forced
  `--rebase-merges` + a python sequence editor; the Sonnet git student dry-ran, aborted, then
  succeeded (32 calls).

The MCP students did these in 4–17 calls and 27–93s. The baseline remains **fair and skilled** — its
losses are non-interactive ergonomics (and, this run, the shared-`.git` ref race), not git competence.

## What worked well
- **Correctness of the work held 40/40 under 40-way concurrency**, across the full T1–T10 surface
  (split, multi-file drop-conflict, deep revise, cherry-pick, working-copy fold, merge editing,
  revert/recover, batch re-date, reorder-conflict+abort). The shared **object store** never corrupted;
  the `Merge branch 'search'` merge was preserved (or correctly edited in T7); `stress/hotfix` stayed
  untouched (T5); no real branch was touched.
- **The multi-tenant server is sound under concurrency** — 22 live sessions, parallel single-writer-per-
  session, no deadlock, the per-session op-log/trash isolation held. The bug is in **shared-`.git` ref
  writes**, a layer below the session model.
- **The two conflict tasks held deterministically** both serially-internally and under load: T3's
  drop-conflict (2 manual resolves auto-cleared 19 descendants) and T10's reorder-conflict + abort
  (every solver did both beats, the abort restoring the exact pre-rewrite state).
- **Reflog recovery is a reliable backstop** for the ref race — 3 students did it unprompted, and the
  other 3 casualties were trivially recovered the same way.

## What bit / improvement targets
1. **Ref-write race on the shared common-dir (new, the run's main finding).** Tracked above; the
   actionable fix is harness-side (separate clones / `gc.auto 0` / verify-from-git). Worth deciding
   whether the engine's export should also defend its ref write (e.g. compare-and-swap on the exported
   ref, retry on lost update) so a concurrent gc can't silently drop a clean export — `t3-op`/`t4-op`
   show the MCP side is not immune.
2. **Export-lag visibility (`t4-op`).** When an MCP export hasn't yet reached the git worktree, an
   agent that checks plain `git` sees stale state and may "fix" a non-problem with `reload_repo` —
   which discards the session's good jj state and forces a redo. `reload_repo`'s discard-and-reimport
   is a sharp edge next to a possibly-lagging export; a "wait for export to settle" or a clearer
   freshly-exported signal would help.
3. **Cost is spawn-warming-dependent, not fixed.** Reading any single run's operator `cost` as "the
   operator tax" is wrong in both directions — run 3's serial spacing made it look cheap, run 4's
   simultaneous cold spawns make it look dear. Real warm reuse sits below both.
4. **Calibration was light by design** (engine rewrite logic byte-identical to run 3). If the engine
   ever changes, re-run full calibration before trusting the answer keys.
