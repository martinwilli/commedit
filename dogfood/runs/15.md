# Run 15 — 2026-07-04 (deferred-tools A/B: does tool-search deferral cut the operator's manifest tax?)

The paired A/B from [`experiments/deferred-tools.md`](../experiments/deferred-tools.md). Question: the
operator's MCP tool schemas are **always-on** — its subagent re-reads the ~12–15k-token manifest every
turn. Claude Code's tool search (defer the schemas, load on demand via `ToolSearch`) promised the same
tax cut for free. Does it deliver? This gates [`cli-plan.md`](../../cli-plan.md).

**Config, logged explicitly (the gap runs 9/13/14 flagged):** model `claude-sonnet-5` (confirmed from
every transcript's `usage` records), effort **not a field the protocol logs** but the teacher launched
under the session's `xhigh` default and op token/turn volume matches run 13/14's xhigh profile — treat
as xhigh. Per-component `$` recovered per README §5 from each student's
`subagents/workflows/<runId>/agent-*.jsonl` (the k≥3 comparative recipe run 14 skipped). **Priced at
Sonnet 5 introductory rates** in effect today through 2026-08-31 (input $2.00, output $10.00,
5-min-cache write $2.50, cache read $0.20 /Mtok); the standard rates are 1.5× across the board, so every
**percentage** below is rate-invariant and only the absolute $ scales.

**Two arms, same day, same fixture (re-provisioned + rr-cache-wiped between), `--plugin-dir plugin` with
the marketplace copy disabled so the CURRENT trimmed operator loads (not the stale 0.5.0 snapshot),
default env (no `ENABLE_TOOL_SEARCH`), k=3, `--model sonnet`.** The **only** variable is the operator's
`tools:` allowlist:

- **Arm A (status quo)** — operator keeps `tools: mcp__…*` → always-on. Solvers op+ctl @k3, plus git @k3
  (a cost anchor; the args-based k=1 plan didn't fire — see below — so git rode along at k=3, harmless).
- **Arm B (flipped)** — the one-line `tools:` deletion → operator defers. Solvers op+ctl @k3.

ctl is `general-purpose` and defers in **both** arms, so it's a same-config **drift anchor**. (The plan's
original arm B — op-deferred + ctl-always-on in one process — is mechanically impossible: `env=false` is
a global switch, confirmed in Phase 1 below. The realized design flips only the operator.)

## Result: 36/36 both arms, all solvers — equal correctness confirmed

Every op and ctl cell passed `verify.sh` on both arms (op 36/36 and ctl 36/36 in each), and git 36/36 in
arm A. Four verdicts (arm B op t7/t10, ctl t2/t11; arm A git t8) needed a second look — the oracle's
`PASS` line was formatted past my grep — but all five carry `pass: true` structured verdicts and exit 0.
No correctness gap anywhere, so the cost delta below is a clean equal-correctness comparison.

## Phase 1 (micro-tests): the deferral mechanism, pinned

| operator | default env | `ENABLE_TOOL_SEARCH=false` |
|---|---|---|
| **with** `tools:` line | always-on (0 ToolSearch) | always-on |
| **without** `tools:` (flipped) | **defers** (ToolSearch → then MCP) | always-on |

Removing the `tools:` line is the whole switch — under default env the operator defers; `env=false` is a
global override that forces everything always-on (so it can't give differential deferral in one process).

## Headline 1: deferring the operator's schemas costs **+29% at equal correctness** — the tax cut backfires

The primary contrast — the **same** operator agent, always-on vs deferred:

| operator solve | median $ [range] | cache_read | cache_create | mean read · create tok |
|---|---|---|---|---|
| **Arm A — always-on** | **0.288** [0.176–0.679] | 53% | 36% | 917k · 50k |
| **Arm B — deferred** | **0.372** [0.218–0.590] | 31% | 57% | 613k · 90k |

Deferral did exactly what it promised to the manifest re-read — `cache_read` fell 917k → 613k tokens
(−33%). But it **moved that weight into `cache_create`**: the operator now pays `ToolSearch` discovery
plus on-demand schema loads, which land as cache *writes*. And a cache write bills at **1.25×** input
versus a cache read's **0.1×** — 12.5× more per token. The cheap re-read it eliminated came back as an
expensive write, netting **+29%**. The drift anchor rules out ambient noise: ctl (deferred in both arms)
was **0.356 → 0.367**, flat.

This is a **fourth outcome the plan's decision framework didn't enumerate** — not "≥10% cheaper," not
"<5% delta," not "correctness drops," but *strictly worse*: identical correctness, materially higher
cost. → **Deferral is not adopted. The operator keeps its allowlist (always-on).** Plan commit #1
(`plugin: Make deferrable`) is dropped.

## Headline 2: the manifest tax is real but **cheap** — the trimmed always-on operator is the *cheapest* solver

Same-day, same-config arm-A comparison across all three current solvers (a valid internal comparison —
not cross-run):

| Arm A solve | median $ [range] | cache_read share |
|---|---|---|
| **op** (always-on, trimmed operator) | **0.288** [0.176–0.679] | 53% |
| **ctl** (deferred, skill-less) | 0.356 [0.247–0.567] | 34% |
| **git** (plain-git baseline) | 0.353 [0.184–0.757] | 46% |

The manifest tax the CLI plan is built around is **confirmed** — the always-on operator does spend 53%
of its cost on `cache_read`, ~917k tokens re-reading the prefix every turn, right at the plan's ~58%
prediction. But that cost is **cheap** (0.1× per token), and after the Jul-3 prompt trim (run 11: −11%)
the operator's fewer-turns efficiency now **more than covers the floor**: op is ~19% cheaper than the
skill-less control and ~18% cheaper than plain git. **The always-on MCP operator is the cheapest of the
three solvers**, which reverses the ordering in `cli-plan.md`'s cost table (git cheapest, op most
expensive). See *Adjudication* — this weakens the CLI's cost premise more than the deferral result
strengthens it.

## Adjudication → `cli-plan.md`

- **The deferral objection to the CLI is refuted.** Tool search does not hand the operator a free tax
  cut — it makes it 29% worse. So "just defer the schemas, no CLI needed" is off the table, and any
  future `cli` solver A/B must baseline against **always-on** MCP (the cheaper MCP regime), never deferred.
- **But the CLI's *cost* premise is now weak.** `cli-plan.md` §"Why consider a CLI" argues the MCP
  operator is the expensive bottleneck (op most expensive, git wins on cost, "fewer-tool-calls advantage
  no longer covers that floor"). Run 15 shows the opposite for the *current* trimmed operator: op is the
  cheapest solver, and its efficiency does cover the floor. The tax is real but cheap. The CLI may still
  win on wall-clock, round-trips, non-MCP harnesses, and human use (the §Adjudication reasons), but the
  pure-cost case that opens the plan needs correcting — see the note appended to `cli-plan.md`.
