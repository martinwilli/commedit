# Run 13 — 2026-07-01 (k=2, full grid, xhigh-effort Sonnet 5)

The **first reasoning-effort A/B**. Runs 9–12 all ran on Sonnet 5 but under whatever reasoning-effort
setting the orchestrating session happened to hold at the time — a value the run docs never recorded,
because effort is a session/harness setting, not something the workflow script controls. This run pins
that variable explicitly: full **12 tasks × 3 solvers (op/ctl/git) × k=2 = 72 students** (+72 verify
agents), same fixture and MCP surface as runs 8–12 (no engine changes since run 12), with the teacher
session — and therefore every `agent()` call in `dogfood/workflow.js`, which inherits it — set to
**Sonnet 5 at xhigh effort**.

**Methodology caveat up front:** "runs 9–12 were low effort" is an *assumption*, not a logged fact —
there is no prior recorded effort value to diff against. Treat the comparisons below as "this run vs.
run 10/12's numbers," not a controlled before/after on a single logged variable.

Orchestrated via the unmodified `dogfood/workflow.js` (only `K` edited 3→2), run with
`Workflow({ scriptPath: 'dogfood/workflow.js' })`. Real `$` recovered per the standard recipe: each
`workflow_agent` progress entry's `agentId` located the student's transcript at
`<session>/subagents/workflows/<runId>/agent-<agentId>.jsonl`, priced at Sonnet per-component rates
(input $3, output $15, cache write $3.75, cache read $0.30 /Mtok).

## Result: 72/72 clean — zero misses, including both of the last two runs' known flakes

| Task | op | ctl | git |
|---|---|---|---|
| all 12 tasks (T1–T12) | 2/2 | 2/2 | 2/2 |

Every one of the 36 cells landed 2/2. Notably clean:

- **T1 (op) — 2/2.** This is the cell that missed in runs 9, 10, 11, and 12 (the operator judging the
  branch "already correctly ordered" and skipping the reorder), always in the 60–70% pass range at k=3.
  Two clean repeats in a row here is consistent with — but, at k=2, well short of proving — higher
  reasoning effort suppressing that specific judgment quirk.
- **T6 (ctl) — 2/2.** Run 12 recorded this run's first-ever T6 partition miss on the skill-less control.
  Clean here.

**Read this with the k=2 caveat the README itself states:** the variance floor for a comparative claim
is k≥3; a single k=2 run without a miss is *suggestive*, not conclusive, that xhigh effort reduces the
T1/T6 flake rates. It's the right next thing to watch, not yet a finding to act on. `fsck` stayed clean
on all 72 verifies too — none of the transient false-positive flakes runs 9/10 saw under concurrent
worktree writes.

**The increase shows up across the whole component stack, not just reasoning tokens hiding in
`output`:** op's `cache_read` rose 693k→776k (+12%) and `cache_create` roughly doubled (~18k→36k);
git's `cache_read` rose 467k→793k (+70%) alongside a genuine call-count jump (13→18 median). Higher
effort isn't just "the model thinks longer before answering" here — it's doing more tool-call
round-trips and re-reading more context per turn, which is why the cost delta is bigger for git (whose
cost is dominated by call count and transcript re-read volume, per run 10's own finding) than for op
(whose cost is dominated by the one-time `cache_create` prompt tax).

**The clearest single number:** run 10's 108 students (k=3) cost $36.13 in solve-agent `$`; this run's
72 students (k=2) cost $36.48 — **essentially the same total dollars bought a third fewer students.**
Per-student average: run 10 $0.335 → run 13 $0.507, **+51%**. Verify-agent cost moved the same
direction but by less (run 12's $0.064/student average → this run's $0.080/student, **+25%**) — a
smaller jump because `verify.sh` is a fixed shell-script call with little for extra reasoning effort to
spend itself on.

## What this run establishes / open question for next time

- **No correctness regression at xhigh effort** — if anything, a clean sweep on the two cells that had
  been the most persistently flaky across four prior runs. Worth a k≥3 xhigh re-run specifically on T1
  and T6 to see if the improvement holds past k=2 noise.
- **Effort is not a free lever.** Going from the runs 9–12 baseline to xhigh cost **~50% more per
  solve-student** and ~25% more per verify-student, driven by more tool calls, larger cache reads *and*
  writes, and longer output — not a narrow "more thinking, same actions" tax. Anyone reaching for xhigh
  to fix a flaky cell should weigh that against just re-running at the existing effort level for k≥3
  and reading the pass-fraction, which is far cheaper.
- **Open methodology gap:** effort level isn't captured anywhere in a run's own metadata (unlike model,
  which run 9 onward states explicitly). If effort A/Bs become a recurring axis, it's worth recording
  the session's effort setting in each run's header the same way the model is recorded now.
- Teardown ran clean.
