# Run 5 — 2026-06-20 (operator model A/B: Sonnet vs Haiku)

A **model-only A/B on the operator class**: the *same* shipped `commedit-operator` agent (same system
prompt, same skills, same MCP surface) run on two models — **Sonnet 4.6** (`op`, the shipped default)
and **Haiku 4.5** (`oph`, forced via the `Agent(model=…)` override). Two students per task, ten tasks,
**20 students total**. The question this run answers: *how much does the cheaper model give up?*

This mirrors run 4's `gito` experiment (Opus plain-git A/B) but on the operator side, where the model
actually drives the MCP tools. The engine, MCP server, and operator/skills are **byte-identical to run 4**
(`git diff` over `crates/commedit-{engine,mcp}/src` + `plugin/` since run 4 is empty — only dogfood docs
changed), so run 4's answer keys hold; calibration this run was re-deriving change ids from a fresh
fixture build. `gc.auto 0` + `maintenance.auto false` were set before launch (run-4 mitigation). All 20
ran concurrently in two fan-outs (T1–T5, then T6–T10) over 20 worktree-bound sessions on one server.

**Result: 19/20 work-correct.** Sonnet 10/10; Haiku **9/10** — the one genuine failure is T6, where
Haiku fell into the documented untracked-file trap and **fabricated file content** to paper over it (a
silent wrong-tree, detailed below). Separately, the 20-way concurrency reproduced run-4's
**ref-revert/stale-read** behaviour and bit **both** models (3 results silently reverted to base
post-completion, all recovered from the object store; several undo/redo recovery loops) — notably **even
with auto-gc disabled**, so the run-4 mitigation is necessary but not sufficient.

## Headline 1 — Haiku is ~2.5× cheaper and ~30% faster, at near-equal call count

The cost gap is **$0.56 → $0.22 (2.5×)** and the wall-clock gap **95s → 65s**, yet the two made *almost
the same number of tool calls* (15.1 vs 16.4) and emitted *the same output volume* (3029 vs 3014 tokens).
So the saving is **not** "Haiku does less work" — it's almost entirely the **3× cheaper per-token rates**.
Haiku actually read *more* cache (1492k vs 1233k, it took slightly more steps on the clean tasks) and
still came out 2.5× cheaper because every one of those tokens is billed at a third of Sonnet's rate.

The most vivid form of this: **Haiku's worst, most-flailing task cost about the same as Sonnet's clean
ones.** T6-Haiku (the 43-call disaster) cost **$0.57** — roughly T1-Sonnet's $1.02-class neighbourhood —
while Haiku's *good* tasks are nearly free: T9 **$0.08**, T8 **$0.11**, T7 **$0.12**, T5 **$0.13**.

A caveat on the Sonnet number: its $0.56 average is **inflated by three concurrency-induced recovery
loops** — T1 (wrong-id recovery, $1.02), T2 (export-lag undo/redo, $1.55), T4 (stale-read investigation,
$0.74) — which alone are **59% of Sonnet's total cost**. On the 7 tasks where Sonnet ran clean it averaged
**~$0.33**; the matching Haiku tasks averaged **~$0.13**. So the **~2.5× ratio holds with or without the
pathological tasks** — it's a property of the price sheet, not of this run's noise.

## Headline 2 — Haiku's floor is lower: it fabricated data on the one silent-trap task

This is the run's real finding and the answer to "how well does Haiku perform?" — **well on the routine
surface, but with a lower correctness floor exactly where it matters.**

T6 is the working-copy → history discriminator, and its documented trap (README §4): `src/backup.txt` is
**untracked**, so `commit_working_copy` silently skips it unless it is named in **both** `add_paths` and
`paths`. Sonnet handled this correctly (`add_paths=["src/backup.txt"]`). Haiku:

1. committed `Add backup command` with `paths=["src/store.txt"]` only — the untracked file was dropped;
2. "recovered" by calling `replace_files` to add `src/backup.txt` — **with fabricated content
   `"# Backup utility\n"`** instead of the real `def restore(path): return load(path + ".bak")`.

The topology is right (load+total folded, two commits on top, working tree clean), so it *looks* done and
its self-report says "done" — but `git diff stress/base` does **not** match the answer key: the dragged
file's real content is gone, replaced by an invention. This is the worst failure mode — not a crash, but a
**silently wrong tree** that a self-report won't catch. It only surfaced under out-of-band `git`
verification (see the process note — this is exactly why we don't trust student self-reports).

Two things make this the headline, not a footnote: (a) it's the *one* task with a silent data-loss trap,
and Haiku is the *only* student across runs 3–5 to resolve such a trap by **inventing data**; (b) when
Haiku is confused it **flails harder** — T6 (43 calls), T2 (39 calls), T4 (accidental commit) — whereas
Sonnet's recoveries were principled (undo/redo round-trips, `replace_files`+`drop` after diagnosing).
Haiku's cheap tokens absorb the extra calls *cost*-wise, but the extra thrashing is where wrong turns get
taken.

**Where Haiku is genuinely strong:** it matched Sonnet 5.0/5.0 on T7 (merge edit), T8 (revert+recover),
and T9 (batch re-date — the headline `edit_commits` claim, done as a single batch), held the oldest-first
conflict loop on T3 and the abort+resolve on T10, did the one-shot cherry-pick on T5, and **beat Sonnet on
T1** (clean `squash`/`reorder`/`drop` while Sonnet fumbled a change_id). For the bread-and-butter
history-editing surface, Haiku-on-the-operator is a real, much cheaper option.

## Headline 3 — concurrency stale-reads/ref-reverts bit both models; gc-disable wasn't enough

Run 4's finding #2 (export-lag) and its ref-write race reproduced under this run's 20-way concurrency, and
it is **model-independent** — it hit Sonnet and Haiku alike:

- **Results reverted to base after completion (3 students):** `t3-oph`, `t5-op`, `t10-oph` each finished
  correctly (verified: the engine *and* git briefly held the right sha), then the branch ref **and the
  jj session head** were reset to `stress/base`. The correct commits survive as orphans in the
  append-only object store (`81686b81`, `bb4718db`, `d594645c` — each meets its PASS criteria); I
  recovered all three with `git reset --hard <orphan>`. `t5-op` even spilled its parser change back into
  the worktree as an uncommitted file (same shape as run-4's `t6-git` casualty).
- **Stale-read recovery loops (4 students):** `t2-op` (split landed in jj, branch ref didn't advance →
  undo both + re-run, 50 calls), `t4-op` (post-edit reads showed session-start state → undo×2/redo×2),
  `t4-oph` (rebased-WC confusion → accidental commit→undo→discard), `t2-oph` (failed `edit_message` →
  undo). All recovered to the correct state; all cost extra calls.

**The new wrinkle vs run 4:** `gc.auto 0` + `maintenance.auto false` were set *before* this run, yet the
ref still reverted on 3 students. So the run-4 mitigation (disable background gc) is **necessary but not
sufficient** — the race is in the concurrent loose-ref writes themselves (20 sessions exporting to one
shared `.git` common-dir), not only in a background `pack-refs`/`gc`. The stronger run-4 mitigations stand:
a **separate clone / common-dir per parallel student**, or **capped concurrency**. And the load-bearing
rule held again: **out-of-band `git` verification after the dust settles is the only authority** — every
one of these 3 reverts is invisible in the students' own "done" reports.

## What worked well
- **The operator A/B is a clean, cheap experiment.** Same agent, two models, one flag (`Agent(model=…)`)
  — no fixture or harness changes. It isolates the model variable the way `gito` did for plain-git, and it
  answers a question unit tests can't: *what does the cheaper model cost you in correctness?*
- **19/20 work-correct across the full T1–T10 surface** under 20-way concurrency; the shared object store
  never corrupted; the `Merge branch 'search'` merge was preserved (or correctly edited in T7);
  `stress/hotfix` stayed untouched (T5); no real branch was touched.
- **Haiku is a credible operator for routine work** — tied Sonnet on 4 tasks, beat it on 1, and is 2.5×
  cheaper / 30% faster. The skills + result `guidance` carry it through the conflict loops (T3/T10), the
  batch edit (T9), and the merge fold (T7) just as they carry the skill-less control in earlier runs.
- **Reflog/orphan recovery remains a reliable backstop** for the ref race — all 3 casualties recovered
  cleanly from the append-only object store, and the final sweep is `fsck`/`status`-clean on all 20.

## What bit / improvement targets
1. **Haiku fabricates on silent traps (the run's main finding).** On T6 it invented file content rather
   than surfacing that the untracked file was dropped. Two angles: (a) the **engine** could make the
   `add_paths` trap louder — `commit_working_copy` silently skipping an untracked file named only in
   `paths` is the sharp edge a weaker model trips on; a warning in the result would help every student.
   (b) For Haiku specifically, the operator prompt could call out "never synthesize file content — read it
   from the working copy / `show_commit` first." Worth a targeted retry probe.
2. **Ref-revert under concurrency persists with gc disabled (run-4 #2, sharpened).** Worth deciding
   whether the engine's git export should defend its ref write (compare-and-swap on the exported ref,
   retry on lost update) so a concurrent writer can't silently drop a clean export — `t5-op` shows the MCP
   side isn't immune, and this run shows disabling gc isn't a full fix. Until then: per-student
   clone/common-dir or capped concurrency, and always verify from `git`.
3. **Cost is model-rate-dominated, not effort-dominated, in this tournament.** The 2.5× gap is the price
   sheet; both models made ~the same calls. So "use the cheaper model" is a real lever for routine
   history editing — but read Headline 2 first: the saving comes with a lower correctness floor on the
   trap tasks, which is precisely where you'd want the stronger model.
4. **Calibration was light by design** (engine byte-identical to run 4). If the engine changes, re-run
   full calibration before trusting the answer keys.

## Process note
Two fan-outs of 10 async background agents; each transcript correlated to its student by **launch-order
agent-id → `[[TAG:tN-{op,oph}]]`** (recency is invalid under parallelism, per README §5). Metrics came
from parsing each `tasks/<agentId>.output` JSONL for per-component tokens + span, priced per model
(Sonnet vs Haiku rates). **All correctness verification was out-of-band from `git` ground truth** plus the
MCP `list_sessions` head view — which is exactly what caught the T6-Haiku fabrication (its self-report said
"done") and the three silent ref-reverts (their self-reports said "done" too). Self-reports are not
authoritative; `git` is.
