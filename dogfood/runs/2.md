**Reading the cost numbers — they don't mean what they look like.** The operator's ~67k billable is
almost entirely *not work*. Decomposed per task its `cache_create` is dead flat at **~64–67k
regardless of the task**, while the actual `input`+`output` is **sub-2k**:

| op task | in | out | cache_create | cache_read |
|---|---|---|---|---|
| t1 | 21 | 1654 | 66433 | 347917 |
| t2 | 22 | 1408 | 67116 | 379894 |
| t3 | 17 | 1030 | 66769 | 220931 |
| t4 | 15 |  776 | 66264 | 157063 |
| t5 | 15 |  884 | 63961 | 153716 |

That flat block is a **per-spawn prompt-materialization tax**: writing the operator's whole prompt
into cache once — base Claude Code system prompt + operator agent definition + all ~40 always-on
`commedit` tool schemas (the bulk) + MCP connect instructions + any loaded skill. It is *independent
of how much the agent then does*, which is exactly why fewer tool calls / less wall-clock don't shrink
it — those savings surface as the tiny in/out and as cheap `cache_read`, never in `cache_create`. Two
consequences for interpreting the table:

- **The tournament maximizes this tax.** Each of the 15 students is a fresh, isolated, serial spawn,
  so every one re-pays the ~66k from a *cold* cache. In a warm session that reuses the operator,
  later calls hit `cache_read` (≈0.1×) instead of re-paying `cache_create` (cache TTL ~5 min). This is
  the pessimistic case for the operator's prompt tax — real repeated use amortizes it.
- **`billable~` flatters plain-git, not the operator.** Dropping `cache_read` looks fair (it's cheap
  *per token*) but git's `cache_read` *volume* balloons — it re-reads its growing transcript on every
  one of its many calls (T5 git: **1.93M** cache_read vs the operator's ~154k). Price it properly and
  the ranking the calls/wall columns already imply reasserts itself: in Sonnet dollars **T5 was ≈$0.34
  for the operator vs ≈$1.2 for git** (operator cost dominated by the one cache_create write; git cost
  dominated by cache_read volume + real in/out across 36 calls). So the operator's efficiency edge is
  *larger* in money than `billable~` shows — its headline number is a fixed prompt floor, git's is
  work that scales with call count. (This is the README §5 "token caveat" in action: report
  `cache_create` vs `cache_read` separately, and don't read the prompt floor as effort.)

**Headline.** The split_commit footgun is **closed**, and that flips run 1's result: the operator is
now the **clear winner** (4.94 vs control 4.78), exactly as [run 1](1.md) predicted. Two deltas:
- **operator ↔ control (skill value):** operator wins on every efficiency axis — ~30% fewer billable
  tokens, ~35% less wall-clock, half the tool calls. Two compounding reasons: (1) on T2 the operator
  no longer loses to the footgun, and (2) the **control pays a `ToolSearch` discovery tax** — for a
  `general-purpose` agent the `mcp__…__*` schemas are *deferred*, so it spends a turn loading them,
  whereas the operator has them always-on. This *reverses* run 1, where the skill-less control edged
  the operator on tokens. (Control still earns its keep on T4, where reading the contract literally +
  ordering the identity edit last preserved the committer email.)
- **(operator|control) ↔ plain-git (the MCP headline):** all three are *correct*, but the MCP
  students are **~5× faster wall-clock** (op 35s vs git 186s avg) and make **~5× fewer tool calls**
  (23 vs 112), and the operator is **~30% cheaper in billable tokens** than git. The gap explodes on
  *mid-history* work: T5 (insert a commit after a low commit) is 3 calls / 27s for the operator vs
  **36 calls / 305s** for git. Plain-git also stumbled twice (T1 first attempt silently no-op'd; T5
  seq-editor dead-end) where the MCP students never did. Token-wise git is *competitive* on a
  single-conflict drop (T3: 61.5k, cheapest) — its cost is wall-clock, call-count and fragility, not
  always tokens.

**What worked well**
- **The split_commit fixes land.** Calibration confirmed the empty-child split is now *refused* with
  an actionable message, and both MCP students solved T2 first-try via the correct "list the moved
  file at its PARENT content" recipe (the operator even read `show_commit include_contents` first, as
  the new tool text suggests). Run 1's single biggest blemish is gone.
- **Correctness held under fire again.** 15/15 exact target histories, every worktree `fsck`/`status`
  clean, descendants rebased, merges preserved (T1/T2/T5 git all kept `Merge branch 'search'`), real
  branches untouched.
- **Inline guidance keeps teaching.** On T3 the skill-less control resolved oldest-first purely from
  the `drop` result's `guidance` field; on T2 the reworded `split_commit` description steered both
  MCP students straight.
- **The operator's edges showed as efficiency, not correctness:** `edit_commits` batch (T4),
  `cherry_pick_commit(new_parent=…)` one-shot mid-history insert (T5), minimal paths throughout,
  always-on tools (no ToolSearch tax).
- **Plain-git, when it worked, was idiomatic:** `commit-tree`+`rebase --rebase-merges --onto` to split
  while preserving the merge (T2), `rebase --onto` + hand-resolve for the drop (T3). The baseline is a
  *fair, strong* control — its losses are about ergonomics, not git skill.

**What bit (improvement targets)**
1. **Committer identity re-stamps on a *second* edit of the same commit (T4).** The operator did
   `edit_commits(author+committer)` then `replace_in_file`; the second rewrite re-stamped the
   committer to the *rewriting* user, silently undoing the requested committer email — and the
   operator *reported* the committer as set. The control avoided it by ordering the identity edit
   last. This is inherent jj/git semantics (committer = whoever last touched it), but it's a latent
   trap: *consider* having `edit_commits`/`edit_identity` optionally pin the committer across a
   subsequent same-commit rewrite, or at least documenting "make the identity edit your last mutation
   on that commit." (Author is sticky; committer is not.)
2. **The `ToolSearch` discovery tax makes the skill-less control look worse than it is.** For a
   `general-purpose` agent the commedit tool schemas are deferred and cost a turn to load. That's a
   harness artifact, not an MCP-surface flaw — but it *inflates* the control's token numbers, so when
   reading the operator↔control delta, remember part of it is "tools always-on" vs "tools deferred,"
   not pure prompt+skill value.
3. **Non-interactive git is fragile in this harness — worse than README §5 assumes.** The scripted
   `GIT_SEQUENCE_EDITOR` technique the baseline recipe leans on is undermined by the harness exporting
   `GIT_EDITOR=true`: git then *skips the todo editor entirely*, so a reorder/insert silently replays
   the unchanged todo (bit the T1 git student once; the T5 git student diagnosed it and abandoned the
   approach for detach+cherry-pick+`rebase --onto`). Not a commedit bug, but it's *why* the git
   baseline is so call-heavy and slow on reorder/insert — and a fair part of the MCP-vs-git story.
4. **commedit still doesn't follow the shell cwd, and it still surprises agents ([run 1](1.md)
   finding #3 recurs).** The T3 control ran a bare `cat server.txt`, got nothing (wrong cwd), and
   wrongly concluded the branch was "off-worktree" — its commedit reads were authoritative and the
   result was correct, but the misdiagnosis shows the trap is still live. Mitigation unchanged: prefer
   commedit reads, or always `git -C <abs>`.
