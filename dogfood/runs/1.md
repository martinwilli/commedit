**What worked well**
- **Correctness was never the problem.** All 10 runs produced the exact target history; every
  worktree ended `fsck`/`status`-clean with descendants correctly rebased and real branches
  untouched. commedit's "git stays a plain repo throughout" invariant held under agent fire.
- **Inline guidance in tool results is doing real teaching.** On T3 the skill-less control
  resolved oldest-first purely because the `drop` result's `guidance` field said to. This
  narrowed the operator↔control gap on the conflict task to almost nothing.
- **`change_id` addressing + self-verifying results** let students chain mutations without
  re-listing, and the topology echoed by each mutation was enough to confirm placement.
- **The operator's edges** showed up as *efficiency*, not correctness: it reached for
  `edit_commits` (batch msg+identity, T4), kept to minimal paths, and on T2 it **self-detected**
  its own wrong split via `show_commit`, `undo`'d cleanly, and resolved the follow-on conflicts
  oldest-first — exactly the resilience the skills coach.

**What bit (improvement targets)**
1. **`split_commit`'s `files` semantics are a footgun.** "the subset to retain (as in
   replace_files)" reads as "list the files to keep," but you must list the file you're moving
   **out**, set to its *parent* content; omitting a changed file silently leaves it in the
   retained commit and yields an **empty child**. The teacher hit it during calibration; the
   operator hit it live (and burned ~20 calls recovering); the control avoided it only by reading
   the description literally. *Fix:* reword the tool/skill — e.g. "list every file the retained
   commit should change, with full content; to push a change to the child, set that file back to
   its parent content. A changed file you omit stays in this commit." Consider rejecting/ warning
   when the computed child is empty.
2. **Interior `drop` conflicts where descendants edited adjacent lines, and the spurious-drop
   auto-resolve did not fire.** Dropping a commit that added a line to `main.txt` conflicted with
   later `main.txt` edits even though the net result was unambiguous. Worth checking whether the
   `Drop` strategy in `try_auto_resolve_spurious` can cover the "added line, later edits nearby"
   case. (We worked around it in the fixture by isolating the drop target in its own file.)
3. **commedit doesn't follow the shell cwd — and that surprises agents.** A control's read-only
   `git` verification failed (`exit 128`) because the bash cwd wasn't the bound worktree; the
   teacher made the *same* mistake and briefly reset the wrong branch. The `work-in-worktree`
   skill covers this, but the trap is easy to hit from plain `git`. *Mitigation:* students should
   prefer commedit reads (`show_commit`, `list_history`) over plain `git`, or always `git -C`.
4. **`list_operations` undercounts effort.** `undo` prunes failed attempts, so the op-log showed
   3 clean ops for T2 even though the operator made ~20 calls. Fine once you know it — grade
   effort from the Tool Log, use `list_operations` for the *landed* result.

**Headline:** the MCP surface is **robust and self-documenting** enough that a skill-less agent
succeeds on every task and *averages slightly higher than the operator* — entirely because of the
one `split_commit` footgun. Close that gap (clearer `split_commit` contract) and the operator's
efficiency edge should make it the clear winner across the board.
