# Run 10 — 2026-07-01 (k=3, Sonnet 5, real $ accounting)

The **first comparative run** since Sonnet 5 became the session default: **k=3** (the README's variance
floor) across the full **12 tasks × 3 solvers × 3 repeats = 108 students**, all on Sonnet 5, with the
per-component `cache_read`/`cache_create`/`input`/`output` `$` accounting runs 1–8 used — which [run
9](9.md) (also on Sonnet 5, but k=2 and workflow-orchestrated) explicitly could not produce. Same fixture
and MCP surface as runs 8–9 (no engine changes since run 8's `feature/plugin-skill-tune` merge).

Orchestrated via the now-mandatory `Workflow` tool (see README §5). Real `$` was recovered per the
recipe added after run 9: each `workflow_agent` progress entry's `agentId` located the student's
transcript at `<session>/subagents/workflows/<runId>/agent-<agentId>.jsonl`, and each was priced with
the standard Sonnet per-component rates (input $3, output $15, cache write $3.75, cache read $0.30 per
Mtok).

## Result: 105/108 first-pass, **107/108 on post-settle re-check — one genuine, reproducible miss**

Two of the three misses were transient (self-corrected on repeat, clean post-settle); **the third is a
real, persistent bug in this run's own reset protocol for T11's git baseline**, not an MCP or model
issue:

1. **T11-git failed 2 of 3 repeats, and the final worktree state stayed FAILED even after settling.**
   Investigating the frozen state: the sibling worktree's *content* was correct (only `Add experimental
   flag` present, no `src/version.txt`), but the **`stress/t11s-git` branch ref itself was stale**,
   still pointing at a repeat-2 commit that included the misplaced `Add version string` — because the
   student, mid-repeat, had run `git checkout stress/feature` (switching the sibling *worktree*'s
   checked-out branch away from `stress/t11s-git` entirely) while fixing up a previous repeat's mistake,
   and later repeats kept operating on the correct *content* without ever moving the `stress/t11s-git`
   *ref* back onto it. `verify.sh`'s T11 check grades the sibling by **branch ref**, not worktree HEAD
   (by design — the ref is the off-worktree-friendly handle), so a worktree that silently drifts onto a
   different checked-out branch leaves that ref permanently stale no matter how many times the reset step
   re-runs. **Root cause is a protocol gap, not a tool gap**: this run's `resetCmd` for T11-git only runs
   `git -C <sibWt> reset --hard stress/feature` between repeats, which resets *content* on whatever branch
   is currently checked out, but never asserts *which* branch that is. **Fix for the next run:** add an
   explicit `git -C <sibWt> checkout stress/t11s-<solver>` before the reset, and tell the git student
   explicitly never to `checkout` a different branch inside a stress worktree — only `reset --hard` /
   `rebase --onto` on the one it's given. Filed as a protocol fix, not a `verify.sh` or MCP finding — the
   MCP-backed op/ctl solvers never touch worktree checkouts this way and both stayed 3/3 clean on T11 all
   three repeats.
2. **T12-op repeat 2: oracle reported `fsck reported corruption`, all content checks passed** — the same
   failure shape as run 9's T5-git miss (an isolated `fsck` false-positive under concurrent worktree
   writes, self-clean on the very next verify against the same worktree). Now observed on **two different
   tasks/solvers across two different runs**, always resolving without any further git operation between
   the failing check and a clean re-check — reinforcing the run-9 read that this is `fsck`'s own
   transient read racing a concurrent pack/gc from a sibling worktree sharing the object database, not a
   correctness regression. Not actionable beyond what run 9 already flagged.

## Real `$` accounting — the headline this run exists to produce

**Solve-agent cost, median [range] over 36 students per class (verify-agent cost is a near-flat
~$0.06 median across all three, excluded below):**

| Solver | Cost median [range] | Cost total (36) | Calls median [range] | Wall median [range] |
|---|---|---|---|---|
| **op** (commedit-operator) | **$0.341** [$0.140–$0.711] | **$12.49** | 9 [5–20] | 55s [26–137] |
| **ctl** (skill-less MCP control) | $0.310 [$0.197–$0.569] | $11.76 | 12 [8–17] | 55s [35–83] |
| **git** (plain-git baseline) | $0.288 [$0.153–$0.779] | $11.88 | 13 [6–33] | 74s [41–222] |

**This is a real reversal from runs 7/8's Sonnet 4.6 findings.** Run 8 (k=1) found the operator the
*cheapest* class by a wide margin (op $3.12 vs ctl $6.70 vs git $7.09 per 12 students — op **less than
half** ctl/git). Here, on Sonnet 5, **the operator is the *most expensive* class on median** — a full
reversal, though the three medians are much closer together (\$0.29–\$0.34) than the run-8 gap ever was.
Digging into the component split explains why: the operator still wins on **call count** (median 9 vs
ctl 12 vs git 13 — the skill-pointed routing still reaches the answer in fewer round-trips, same
mechanism as before) and has the **lowest `cache_create`** (~18k tokens median — its one-time prompt tax
is still small), but now carries the **highest `cache_read` volume by far** (~693k tokens median, vs ctl
~371k and git ~467k) — meaning whatever the operator re-reads on *every* turn (skills + tool schemas +
accumulated context) got markedly larger under Sonnet 5, or Sonnet 5 re-reads more of it per turn than
4.6 did. Even at the cheap `cache_read` rate (0.1× input), that volume is now big enough to erase the
per-call efficiency win. **This is the concrete, actionable finding real accounting was built to catch**
— a call-count win that no longer translates to a cost win is invisible to any metric except the
component breakdown, and would have been reported backwards using totals or call counts alone.

- **git remains the slowest and most variable class** (median wall 74s vs op/ctl ~55s, and the widest
  cost range — $0.153–$0.779 — driven by the same non-interactive-rebase friction runs 7/8 documented:
  T1 (20 calls/148s median), T7's scripted merge-rebase (one repeat hit 33 calls/222s/$0.779), and T9's
  per-commit re-date/re-identify (20-23 calls/134s median), all cases where a single `edit_commits`- or
  `squash_commit`-class MCP call replaces a multi-stage scripted sequence-editor dance.
- **No task showed a correctness delta between op and ctl** — every MCP student (48 total) reached
  `verify.sh` PASS on first completion except the one T12-op fsck flake. The skill tuning validated in
  run 8 still routes correctly at k=3 on Sonnet 5.

## What this run establishes / known gaps

- **Sonnet 5 does not regress correctness** at the README's k≥3 variance floor: 107/108 post-settle, two
  isolated flakes (one now-familiar `fsck` false-positive, one protocol-bug-induced git failure), zero
  MCP tool-routing misses.
- **The operator's `$` advantage from runs 7/8 does not carry over to Sonnet 5 as measured here** — it's
  now a wash-to-slightly-more-expensive on median cost, despite still winning on calls. This is a genuine
  model-behavior finding (larger/more frequent context re-reads), not a regression in the MCP surface or
  the skills — worth re-checking after a future Sonnet point release to see if it's an artifact of this
  specific model version or a durable shift in how skill-heavy prefixes get read.
- **Fixed for next run: the T11-git reset protocol gap.** Add an explicit branch-checkout assertion
  before every reset of the sibling worktree, and forbid the git student from switching that worktree's
  checked-out branch — this is a workflow-script fix, not a README or MCP-surface fix, and should be
  folded into the next run's script (see run 9's script, referenced from README §5, as the template to
  patch).
- **Teardown ran clean**: all 45 `stress/*` branches and worktrees removed, `rr-cache` cleared.
