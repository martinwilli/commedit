# Run 9 — 2026-07-01 (k=2; first run on Sonnet 5)

A **k=2** run of the full grid — **12 tasks × 3 solvers × 2 repeats = 72 students** — with one deliberate
change from every prior run: the model for **all three solver classes** (operator, control, git) is
**Sonnet 5** (`claude-sonnet-5`), not Sonnet 4.6. Martin wanted a first look at whether the new model
shifts anything before it becomes the session default. Same 12-task fixture as run 8 (T1–T12, T11
cross-branch included), same MCP surface (no engine changes since run 8's `feature/plugin-skill-tune`
merge landed on `master`).

**Orchestration note (methodology deviation):** this run was driven via the `Workflow` tool instead of
manually spawning/scoring each student one at a time as runs 1–8 did. That gets a real, deterministic
72-cell fan-out with immediate out-of-band verification per repeat, but the workflow harness does not
expose the per-component token breakdown (`cache_read` vs `cache_create` vs `input`/`output`) that
earlier runs priced in `$` — only aggregate token counts, tool-call counts, and wall-clock per student.
**Cost is reported here as total-token medians, not `$`** — not directly comparable line-for-line to
runs 1–8's `$` figures. Correctness, call counts, and wall-clock are directly comparable.

## Result: 70/72 pass on first completion, **72/72 on post-settle re-check**

Both misses were **within-cell flakiness on repeat 1 or 2 of the same cell**, not a systematic miss —
running `verify.sh` again against the final worktree state (after all repeats had landed) showed **every
cell clean**, including the two that had a failing repeat:

1. **T1-op, repeat 1: the operator judged a reorder unnecessary and was wrong.** Its own tool log says
   *"'Add util helper format_row' was already correctly ordered before 'Use format_row in main' so no
   reorder was needed"* — but the oracle failed on exactly that check (`parent of 'Use format_row in
   main' is 'Add parser'`, want `'Add util helper format_row'`). The operator squashed the fixup and
   dropped the Debug commit correctly, then skipped `reorder_commit` on a bad read of the graph. Repeat 2
   (fresh cold spawn, same cell) did the full 3-mutation job including the reorder and passed. This is a
   **model judgment miss, not a tool-routing miss** — worth watching across future k≥3 runs to see if it's
   a one-off dice roll or a Sonnet 5-specific pattern (second-guessing a step as redundant).
2. **T5-git, repeat 2: oracle reported `fsck reported corruption`, all content/placement checks passed.**
   The student's own recovery (discovering `rebase.autosquash=true` was silently interfering, switching
   to `--no-autosquash`, fixing its todo-line parser for this git's `sha # message` format) was clean,
   and every content assertion (cherry-picked commit present, author preserved, `[BUG-123]` stripped,
   position correct, `stress/hotfix` untouched, clean tree) passed — only the `fsck` connectivity check
   failed. The **post-settle re-run of the same worktree passed fsck cleanly**, with no further git
   operations in between. Read together with the run 7/8 ref-race history (concurrent worktrees sharing
   one object database), this smells like a **transient fsck read racing a concurrent pack/gc from a
   sibling worktree's rebase**, not real corruption — but it's exactly the kind of signal the mandatory
   post-settle re-check exists to catch, so it's recorded here rather than waved off.

Both flaky cells resolved clean on the mandatory post-settle oracle re-run; teardown (worktrees,
branches, `rr-cache`) completed with no leftover state.

## Sonnet 5 vs the run 7/8 Sonnet 4.6 baseline

- **Correctness: no regression.** 72/72 post-settle, same as run 7 (66/66) and run 8 (36/36). The two
  in-run misses were flakiness (a judgment slip and an apparent transient fsck), both self-corrected on
  repeat and clean on re-verify — not a new failure mode.
- **Token cost pattern looks different, but isn't apples-to-apples.** Runs 7/8 measured `$` from
  `cache_read`/`cache_create` component pricing and found the operator the *cheapest* class by a wide
  margin (run 8: op $3.12 vs ctl $6.70 vs git $7.09 per 12 students) because its skill-pointed routing
  needed far fewer calls, and its always-on prefix is a cheap `cache_read`, not an expensive
  `cache_create`, on a cold spawn. Here, using **raw token counts** (this harness's only available
  metric), the operator's **median token count is the highest** of the three classes (49.2k vs ctl 33.0k
  vs git 24.1k) despite having the **lowest median call count** (9.5 vs ctl 12 vs git 10.5) — consistent
  with the same "operator prefix is a big flat load per cold spawn" mechanism runs 7/8 described, but
  without the cache-component pricing split this run can't confirm whether that load is still landing on
  the cheap `cache_read` path under Sonnet 5 the way it did under 4.6. **This is the one open question a
  future run should re-check with per-component metrics** (drop back to manual Agent-tool orchestration,
  or extend the workflow script to parse each subagent's `subagents/agent-*.jsonl` directly, per §5
  "Metrics capture") before drawing a Sonnet-5-changed-the-economics conclusion.
- **Wall-clock: git remains the slowest class**, consistent with runs 7/8 (median 71.0s vs op 60.6s vs
  ctl 55.2s) — non-interactive scripted rebases are still the friction point regardless of model.
- **No new tool-routing regressions.** All 24 MCP students (op+ctl) reached the right tool for T11's
  cross-branch move and T12's content-blame path on both repeats — the `feature/plugin-skill-tune` skill
  tuning validated in run 8 still holds on Sonnet 5.

## What this run establishes / known gaps

- **Sonnet 5 is safe to use for this workload** — no correctness regression at k=2, no new tool-misuse
  pattern, git baseline still the slowest/most call-heavy class.
- **The op-token-vs-op-calls divergence (highest tokens, lowest calls) is worth a follow-up run with
  real cache-component pricing** — this run's workflow-based orchestration traded that visibility away
  for a faster, more automated fan-out. A future comparative run should either restore manual
  per-student `$` accounting or extend the workflow script to read each subagent's transcript file
  directly for the `cache_read`/`cache_create` split.
- **T1-op's missed reorder and T5-git's fsck flag are both single-repeat events that self-corrected** —
  neither reproduced on repeat 2 (T1) or the post-settle re-check (T5). Not actionable as a tool or skill
  fix; worth keeping an eye on at k≥3 to see if either recurs.
- **Teardown ran clean**: all 45 `stress/*` branches and worktrees removed, `rr-cache` cleared.
